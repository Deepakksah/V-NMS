Scope: 20 Failure Scenarios Across 8 Layers

When the V-NMS dashboard reports a device as Offline, Missing Ports, Blank Storage/Disk IO, or Zero Telemetry, the underlying cause exists across one of the eight infrastructure layers below. This SOP covers all 20 verified real-world conditions, technical root causes, and CLI resolutions.

1. Rapid 30-Second Diagnostic Decision Flowchart

2. Category 1: Physical & Data Link Layer Failures (Layer 1 & Layer 2)

Condition 1.1: Physical Cable Disconnection, Power Loss, or Switch Port Err-Disabled

  • Symptom: Target host exhibits 100% packet loss (Destination Host Unreachable or Request timed out).
  • Root Cause: Power supply failure, disconnected patch cord, or switch port entered err-disabled state.
  • Diagnostic Command: arp -a | findstr "<TARGET_IP>"
  • Resolution: On upstream switch (Cisco Catalyst): interface <PORT_ID> → shutdown then no shutdown.

Condition 1.2: VLAN Assignment Mismatch

  • Symptom: Physical link LED is green, but host cannot communicate with subnet.
  • Root Cause: Switch port assigned to wrong Access VLAN.
  • Resolution: interface <PORT_ID> → switchport access vlan 10.

Condition 1.3: Duplicate IP Address Conflict (ARP Poisoning / IP Clash)

  • Symptom: Telemetry flaps intermittently; MAC address in arp -a keeps changing.
  • Root Cause: Two hosts configured with the identical static IP.
  • Resolution: Trace conflicting MAC on switch via show mac address-table address <MAC> and assign a unique IP.

3. Category 2: Network & Routing Failures (Layer 3)

Condition 2.1: Missing Default Gateway or Inactive Inter-VLAN Routing

  • Symptom: Local subnet works, but foreign subnets (192.168.10.0/24) report 100% loss.
  • Resolution: Verify default route on V-NMS host (Get-NetRoute) and enable ip routing on Core Switch.

Condition 2.2: Subnet Mask Mismatch

  • Symptom: Target receives traffic from some hosts but cannot reply to V-NMS monitoring server.
  • Resolution: Correct subnet mask on target host network adapter to match subnet (e.g. 255.255.255.0).

Condition 2.3: MTU Mismatch & UDP Packet Fragmentation Drop

  • Symptom: Small pings succeed, but large SNMP bulk walks hang or time out.
  • Diagnostic Command: ping <TARGET_IP> -f -l 1472
  • Resolution: Configure MTU/MSS clamping on VPN tunnels (ip mtu 1400, ip tcp adjust-mss 1360) and allow fragmented UDP.

4. Category 3: Security & Firewall Filtering Failures (Layer 4 & Layer 7)

Condition 3.1: Host Firewall Dropping ICMP Echo Requests

  • Symptom: Web/SSH accessible, but ICMP Ping fails, marking host "DOWN".
  • Fix (Windows): netsh advfirewall firewall add rule name="Allow ICMPv4-In" protocol=icmpv4:8,any dir=in action=allow
  • Fix (Linux RHEL 9): sudo firewall-cmd --permanent --add-icmp-block-inversion && sudo firewall-cmd --reload

Condition 3.2: Perimeter Firewall / IPS Rate-Limiting & Port Scan Blacklisting

  • Symptom: Scan discovers first 10-15 devices, then all subsequent targets stop responding for 5 minutes.
  • Root Cause: Next-Gen Firewall (Check Point / Palo Alto) IPS detects 40 concurrent port scan threads and drops scanner IP.
  • Resolution: Add V-NMS Server IP (172.168.1.14 and 172.168.1.11) to the Firewall IPS Whitelist / Exception Table.

5. Category 4: SNMP Telemetry & Polling Failures

Critical Rule: When ICMP Ping is alive and responsive, but Interface Bandwidth (0 Mbps), Traffic Graphs, Memory, or CPU utilization remain at 0% or blank, the issue resides in the SNMP agent configuration in 95% of cases.

Condition 4.1: SNMP Daemon Service Stopped or Uninstalled

  • Fix (Windows): Add-WindowsCapability -Online -Name "SNMP.Client~~~~0.0.1.0" then Start-Service SNMP.
  • Fix (Linux RHEL/Ubuntu): sudo systemctl enable --now snmpd

Condition 4.2: SNMP Community String Mismatch

  • Resolution (Cisco Switch): snmp-server community public RO

Condition 4.3: SNMP "Allowed Management Hosts" ACL Restriction

  • Resolution: Whitelist V-NMS Server IPs (172.168.1.14 and 172.168.1.11) in target SNMP Service properties or /etc/snmp/snmpd.conf.

Condition 4.4: SNMPv3 EngineID, User, or Cipher Authentication Failure

  • Resolution: Verify credentials and encryption ciphers on switch: show snmp user and show snmp engineID.

Condition 4.5: High CPU Starvation Dropping Management Traffic

  • Symptom: Ping latency jumps from 0.5ms to 300ms; SNMP polling intermittently drops.
  • Resolution: Check switch CPU via show processes cpu sorted and mitigate control-plane loops.

6. Category 5: Host OS & Socket Binding Failures

Condition 5.1: Database / Microservice Bound Strictly to Localhost (127.0.0.1)

  • Resolution (PostgreSQL): Set listen_addresses = '*' in postgresql.conf and authorize subnet in pg_hba.conf.
  • Resolution (MongoDB): Set bindIp: 0.0.0.0 in /etc/mongod.conf.
  • Resolution (Redis): Set bind 0.0.0.0 in /etc/redis/redis.conf.

Condition 5.2: Windows WMI / RPC Remote Error (0x800706BA "The RPC Server is Unavailable")

  • Resolution (Run on target Windows host): 
    winrm quickconfig -q
netsh advfirewall firewall set rule group="Windows Management Instrumentation (WMI)" new enable=yes
netsh advfirewall firewall set rule group="Remote Administration" new enable=yes

Condition 5.3: Disk Partition Full (100% Usage / Read-Only Filesystem)

  • Symptom: Target responds to ping, but SSH fails and telemetry stops completely.
  • Resolution: Check df -h / and purge bloated logs under /var/log.

7. Category 6 & 7: Time, Cryptography, & V-NMS Pipeline Health

Condition 6.1: NTP Clock Skew / Time Drift Exceeding 300 Seconds

  • Symptom: Missing data gaps in historical charts; Kerberos / SNMPv3 authentication fails.
  • Fix (Windows): w32tm /config /manualpeerlist:"172.168.1.10" /syncfromflags:manual /update && w32tm /resync
  • Fix (Linux Chrony): sudo chronyc add server 172.168.1.10 iburst && sudo chronyc makestep

Condition 6.2: SSL/TLS Cipher Suite & Certificate Mismatch

  • Symptom: Cockpit (Port 9090) or API reports An unexpected error occurred on a send.
  • Resolution: Renew expired certificates and ensure modern TLS 1.2+ cipher support.

Condition 7.1: VNMSService Inactive or Terminated

  • Resolution: Get-Service -Name VNMSService | Restart-Service

Condition 7.2: PostgreSQL Database Connection Pool Exhaustion

  • Resolution: In postgresql.conf, set max_connections = 250 and restart PostgreSQL service.

💡 Network Engineering 3-Second Verification Command:
Execute in PowerShell to test complete Layer-3 routing and Layer-4 service reachability in one step:
Test-NetConnection -ComputerName <TARGET_IP> -Port <PORT_NUMBER>
When TcpTestSucceeded : True is returned, physical cabling, inter-VLAN routing, and firewall policies are 100% verified, isolating the issue purely to host authentication or service configuration.
